# zclip — Project Handoff Document

## What is zclip?

`zclip` is a persistent clipboard history daemon written in Zig, built for macOS. It runs silently in the background, saves every clipboard entry to a local SQLite database, and lets you search and retrieve past entries from the terminal — with no retention limits.

**The problem it solves:** Raycast's free clipboard history only retains entries for a few weeks. When you only remember a fragment of something you copied weeks or months ago, it's gone. `zclip` keeps everything indefinitely in a local SQLite file you fully own and can query directly.

## POC Scope (Weekend Build)

The POC should be achievable in a weekend and validate the core loop: watch clipboard → save to DB → retrieve by search.

### Features

**1. Clipboard polling daemon**
- Poll `NSPasteboard` every second via Zig's C FFI (`@cImport`)
- Detect changes via `NSPasteboard.changeCount` (monotonic integer that increments on every pasteboard write). Cheap compare — no need to read content or hash on each tick.
- Only read content + insert when `changeCount` differs from last seen value
- **Text-only for POC.** Skip the tick if `availableType(in: [.string])` returns nil (images, files, RTF deferred to post-POC)
- **Skip concealed entries.** Password managers (1Password, Bitwarden, Keychain) mark sensitive items with `org.nspasteboard.ConcealedType` or set `NSPasteboardTypeAutoGenerated`. Check pasteboard types and skip these — otherwise every copied password lands in `history.db` forever in plaintext
- **Single-instance enforcement.** Acquire `flock` on `~/.local/share/zclip/zclip.pid` at startup; exit if already held. Two daemons would race-insert duplicates.
- **Signal handling.** Trap SIGINT/SIGTERM, close DB cleanly, release pidfile

**2. SQLite persistence**
- Store history at `~/.local/share/zclip/history.db`
- Auto-create DB and table on first run
- Enable WAL mode on connect (`PRAGMA journal_mode=WAL`) so daemon writes don't block CLI reads
- Hash stored as 32-byte `BLOB` (raw SHA256) for content-level dedup. Not unique-constrained — re-copying the same content is a legitimate event that updates recency.
- Schema:
```sql
CREATE TABLE IF NOT EXISTS entries (
  id        INTEGER PRIMARY KEY,
  content   TEXT NOT NULL,
  hash      BLOB NOT NULL,             -- raw SHA256 (32 bytes)
  copied_at INTEGER NOT NULL           -- unix epoch seconds, set explicitly by daemon
);
CREATE INDEX IF NOT EXISTS entries_hash_idx ON entries(hash);
CREATE INDEX IF NOT EXISTS entries_copied_at_idx ON entries(copied_at);
```
- On clipboard change: look up most recent entry with matching `hash`; if found, `UPDATE entries SET copied_at = ? WHERE id = ?`. Otherwise `INSERT`. Keeps recency accurate without exploding storage on repeated re-copies.

**3. `zclip search <keyword>` command**
- POC uses `WHERE content LIKE '%keyword%' ORDER BY copied_at DESC LIMIT 50`
- Print matching entries with ISO timestamps (POC) and IDs. Relative-time formatting deferred to post-POC.
- Truncate `content` display to ~120 chars + `…` so a copied 5MB log dump doesn't flood the terminal
- Example output:
```
2026-05-25T14:02  id=42  SELECT * FROM users WHERE id = $1
2026-05-24T09:18  id=31  git commit -m "fix connection pool timeout"
2026-05-22T11:40  id=12  https://example.com/very/long/url/that/gets/trunc…
```
- **Scaling note.** `LIKE` is fine up to ~10k rows. Migrate to SQLite FTS5 (ships with macOS `libsqlite3`) when search latency becomes noticeable.

**4. `zclip use <id>` command**
- Retrieve entry by ID from DB
- Write it back to `NSPasteboard`, ready to paste
- **Suppress the feedback loop.** The write will increment `changeCount` and the daemon would otherwise observe its own write. Two options:
  - (a) Have `use` directly bump that entry's `copied_at` and write a sentinel (last-seen `changeCount`) into a small `state` table that the daemon reads on next tick to skip exactly one change, or
  - (b) Add a custom pasteboard type (e.g. `dev.zclip.origin`) when writing from `use`; daemon ignores any tick where that type is present.
  - Option (b) is cleaner and matches how other clipboard tools (Maccy, Paste) handle this.

## Recommended File Structure

```
zclip/
  src/
    main.zig        # CLI entry point, subcommand routing
    daemon.zig      # Polling loop, change detection, signal handling
    clipboard.zig   # NSPasteboard C FFI wrapper (read/write/changeCount/types)
    db.zig          # SQLite connection, WAL pragma, insert/upsert/search
  build.zig
  build.zig.zon    # Empty for POC — SQLite linked as system lib (-lsqlite3),
                   # AppKit via -framework AppKit. Add Zig package deps later.
```

Schema lives inline in `db.zig` for the POC. A `migrations/` directory + a tiny `PRAGMA user_version`-based runner is worth adding once the schema changes for the first time (e.g. when adding the `type` column or FTS5 index).

## Key Technical Areas

| Area | Details |
|---|---|
| Clipboard access | `NSPasteboard` via Zig C FFI (`@cImport`, `@cInclude`). Key APIs: `changeCount`, `availableType(in:)`, `string(forType:)`, `setString(_:forType:)`, `types` |
| Database | SQLite via C FFI (libsqlite3, ships with macOS). WAL mode on connect. |
| Daemon loop | `std.time.sleep` in a `while(true)` loop with `changeCount` polling; SIGINT/SIGTERM handler for clean shutdown |
| Concurrency | One daemon enforced via `flock` on a pidfile. CLI subcommands open the DB read-only where possible. |
| Hashing | `std.crypto.hash.sha2.Sha256` for content dedup |
| CLI parsing | `std.process.args` or a lightweight arg parser |
| Daemon start (POC) | Manual: `zclip daemon &` from a terminal. `launchd` `.plist` deferred to post-POC. |

## Extension Points (Post-POC)

These are naturally additive — each is its own mini milestone:

| Feature | What you build | What you learn |
|---|---|---|
| `zclip status` | Show total entries, DB size, last copied | Basic DB aggregates |
| `zclip pin <id>` | Mark entries so they never get evicted | Soft-delete / flag patterns |
| FTS5 search | Replace `LIKE` with SQLite FTS5 virtual table | Schema migration, indexing |
| Fuzzy search | Layer fuzzy matching on top of FTS5 results | Zig string algorithms |
| Relative timestamps | "3 mins ago" formatting in `search` output | Time formatting in Zig |
| Non-text clipboard | Handle images, files, RTF; add `mime_type` column | Pasteboard type system |
| Entry type tagging | Detect URLs, code, file paths; add `type` column | Content parsing, DB schema evolution |
| Auto-eviction | Delete entries older than N days on startup | Scheduled work in daemon |
| `zclip create <name>` | Save named snippets (bridges to a `zsnip` feature) | Named query patterns |
| `--dry-run` flag | Preview what would be evicted | CLI flag design |
| Launch at login | Generate and install a macOS `launchd` `.plist` | macOS system integration |
| Encrypted storage | Encrypt content at rest with a local key (e.g. age/libsodium) | Zig crypto stdlib |
| Per-app allowlist/denylist | Skip entries copied from specific apps | NSRunningApplication, frontmost app detection |

## Why This Is Good Zig Practice

- **C FFI** — macOS clipboard and SQLite are both C APIs. You'll use `@cImport`, `@cInclude`, and manage C pointers, which is core Zig knowledge.
- **Manual memory management** — Zig has no GC. Managing allocators for DB results and clipboard strings will build real fluency.
- **Daemon architecture** — A long-running process with a polling loop, signal handling, and graceful shutdown.
- **Error handling** — Zig's explicit error unions (`!T`) will be exercised heavily with C interop.

## Connection to Ghostty

Ghostty (written in Zig, macOS-native terminal emulator) uses `NSPasteboard` for its own clipboard handling. Building `zclip` gives you direct hands-on experience with the same macOS APIs and Zig C FFI patterns used in Ghostty, making it a natural on-ramp before contributing to that project.

## Suggested First Session Plan

1. Set up `build.zig` with SQLite (`-lsqlite3`) and macOS framework linkage (`-framework AppKit`)
2. Write `clipboard.zig` — wrap `NSPasteboard`: read `changeCount`, check available types, get/set string, expose a way to write with a custom origin type
3. Write `db.zig` — open SQLite, set `PRAGMA journal_mode=WAL`, create table + indexes, implement upsert-by-hash and search-by-keyword
4. Wire up `daemon.zig` — acquire pidfile lock, install signal handlers, poll every second using `changeCount`, skip concealed/non-text/own-origin entries, call upsert
5. Add `main.zig` subcommand routing for `daemon`, `search`, `use`
6. Test end-to-end:
   - Copy something → `zclip search` finds it
   - Re-copy same content → `copied_at` updates, no duplicate row
   - Copy from 1Password → entry is NOT in DB
   - `zclip use <id>` → content on pasteboard, no new entry created
   - SIGINT the daemon → exits cleanly, pidfile released

## Zig Version Pinning

Target minimum Zig version: **0.16.0**.

Originally planned for 0.15.2, but the local toolchain on this machine is 0.16.0, and 0.16 introduced changes that can't be expressed in 0.15.2 source (notably `pub fn main(init: std.process.Init)` and the `std.Io.File.Writer` API). Pinning to 0.15.2 while writing 0.16-only code would be a lie. If you want to target 0.15.2, install it (`zigup 0.15.2`) and downgrade `main` plus any `std.Io` usage before changing the pin back.

Zig is pre-1.0 and breaks meaningful APIs in every minor release. Pin explicitly so contributors (and future-you) don't waste time on cryptic compile errors.

**1. Repo-level pin** — `.zigversion` file at repo root, contents:
```
0.16.0
```
Tools like `zigup` and `asdf-zig` read this and auto-switch.

**2. Build-level pin** — in `build.zig.zon`:
```zig
.minimum_zig_version = "0.16.0",
```
Older compilers refuse to build the project.

**3. Known breaking changes to watch for**
- **0.15 "Writergate":** `std.io.Writer`/`Reader` interfaces replaced. Old `writer.print(...)` patterns may not compile. New API lives under `std.Io`. Most code online predates this.
- **0.15:** `usingnamespace` keyword removed entirely.
- **`std.Build` API:** signatures of `b.addExecutable`, `b.addModule`, link calls have shifted across 0.13 → 0.14 → 0.15. Always check the release notes for the version you're targeting.
- **Allocator API:** small renames every release; the compiler error usually points you straight to the replacement.

**4. Safer-than-LLM source of truth**
LLMs (including the one helping you build this) have inconsistent coverage of recent Zig versions. Treat any LLM-generated Zig as a draft. Always:
- Compile with the pinned version immediately
- Cross-check stdlib symbols against [the 0.15.2 release notes](https://ziglang.org/download/0.15.2/release-notes.html) and [the auto-generated stdlib docs](https://ziglang.org/documentation/0.15.2/std/)
- When in doubt, the compiler error message is authoritative

C FFI patterns (`@cImport`, `@cInclude`, `@ptrCast`, `extern fn`) have been stable for years — those are the lowest-risk part of this project. The risk concentrates in `build.zig` and any I/O you do with the standard library.

## Known Tradeoffs

- **DB growth is unbounded by design.** "No retention limits" was the point — but the file will grow without end. You own the SQLite directly, so pruning by hand (`DELETE WHERE copied_at < …`) is always available. Auto-eviction is a post-POC extension.
- **Plaintext at rest.** Even with concealed-type filtering, anything you copy that isn't marked concealed (API keys pasted from a doc, tokens in terminal output) ends up readable on disk. macOS FileVault covers the at-rest threat for a stolen laptop, but anyone with your user account sees plaintext. Encryption is on the extensions list; treat the DB as sensitive in the meantime.
- **Polling latency.** A 1-second poll means a copy made in the gap, immediately overwritten, is lost. macOS doesn't expose a public pasteboard-change notification, so polling is the standard approach. 1s is a reasonable tradeoff between CPU and miss-rate.
